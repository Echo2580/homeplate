## 1. 项目与证据边界

homeplate 面向家庭、教室和办公室等空间中的家电管理。第一版计划让空间共用一份档案，通过二维码查看设备；管理者拍铭牌建档，管理保修和保养，接收主动提醒，并在设备故障时咨询 AI。

### 1.1 第一版的九个模块

| 模块 | 在用户任务中的作用 |
|---|---|
| 空间共享档案 | 将同一空间的设备资料集中起来，扫码查看，修改需要管理权限 |
| AI 建档 | 通过铭牌识别减少手工输入，保留核对与手动填写 |
| 家电档案 | 保存和维护设备信息及铭牌照片 |
| 保修管理 | 根据购买日期和保修期计算到期日与剩余时间 |
| 保养管理 | 生成和调整任务，完成后自动安排下一期 |
| 首页 | 汇总当前空间设备与优先处理事项 |
| 基础保障 | 保证手机可用、访问受控、数据可靠且可恢复 |
| 主动提醒 | 主动通知保修临期、保养到期和逾期事项 |
| AI 助手 | 结合所选设备开展文字多轮问答和故障初步排查 |

不纳入第一版的主要内容包括个人账号与成员角色、独立维修记录、完整保养历史与费用统计、维修派单、批量建档、深色模式和小程序。具体边界仍以范围基准为准。

### 1.2 当前可以确认什么

| 信息类型 | 当前口径 |
|---|---|
| 用户已确认的决定 | 九个模块纳入第一版；采用空间共享档案、查看二维码和管理密码，不要求每个人注册 |
| 当前代码起点 | 现有正式代码包含铭牌识别、设备增删改、保修计算、保养任务增删改与续期、照片存档、首页和整站访问密码；存储已切换为 SQLite，首次启动自动建表 |
| 尚需补齐的正式业务能力 | 空间及二维码权限、空间数据隔离、主动推送、AI 助手、基础备份恢复等，尚未在现有正式业务入口中接入 |
| 存储迁移核对 | 2026-10-19 核对迁移了 6 台设备、3 条保养任务和 4 个照片文件，逐字段与 ID 一致；这是迁移时点的记录，不是持续实时统计 |
| 不能据此确认的事实 | 服务是否在线、公网是否部署成功、最新识别耗时，以及家人是否已独立完成操作 |
| 待验证的需求判断 | 使用者是否愿意录入、是否更愿意扫码查询、提醒是否有帮助、AI 建议是否能支持初步判断 |

本分析中的需求判断来自已确认范围与代码核对；存储切换另已完成迁移一致性核对和隔离回归测试。未据此宣称真实模型、手机使用或九模块整体验收通过。历史日志中的测试、设备数量和网络状态不作为持续当前结果。

## 2. JTBD：用户在什么情况下需要这个产品

### 2.1 用户按承担的任务划分

| 使用者 | 家庭中的例子 | 功能场所中的例子 | 主要任务 |
|---|---|---|---|
| 空间设备管理者 | 负责记录设备、安排保养的家人 | 负责教室或办公室设备的人员 | 建档、维护资料、处理提醒、完成保养、咨询故障 |
| 空间设备查看者 | 想查询保修或保养状态的家人 | 需要了解所在空间设备信息的师生或员工 | 扫码找到设备，查看允许公开的信息 |

这里的区分用于说明任务和权限，不代表第一版建立个人成员账号或追踪具体操作人。同一个人也可能在不同空间承担不同任务。

家庭是主要试用场景，教室用于验证同一套空间共享方式能否成立。年龄、职业和设备数量不设为已经证明的用户门槛；原稿中的具体画像不能代替访谈结果。

### 2.2 任务陈述

沿用“当……时，想要……，以便……”的表达，同时检查现有替代方式及其不足。

| 编号 | 任务 | 当……时 | 想要…… | 以便…… | 可能的替代方式与不足，待访谈核实 |
|---|---|---|---|---|---|
| J1 | 建档 | 新设备安装或整理现有设备时 | 拍铭牌快速建立可核对的档案 | 以后不用重新寻找型号和购买信息 | 手抄、相册、纸质单据；信息可能分散，型号输入费时 |
| J2 | 查询 | 家人或场所使用者需要了解某台设备时 | 扫码进入对应空间并找到设备 | 自行查到保修和保养情况 | 询问负责人、翻聊天记录；依赖他人及时答复 |
| J3 | 保修判断 | 准备联系售后或保修临期时 | 看到已登记政策对应的到期日和剩余时间 | 带着设备资料联系售后 | 凭记忆估计；可能误记购买日期和保修期限 |
| J4 | 保养处理 | 保养到期或收到提醒时 | 知道本次做什么，处理后更新下一次日期 | 不必每次重新计算周期 | 凭感觉或手设日历；计划与完成状态可能脱节 |
| J5 | 故障初步排查 | 设备异常但不清楚原因时 | 基于具体设备获得可执行的检查建议 | 判断可以安全自检还是应找专业人员 | 泛化搜索、普通聊天问答；需要重复描述设备，建议可能不适用 |

涉及建档、修改信息、完成保养或使用 AI 的操作需要管理授权；扫码查看不授予修改权限。更换设备、选择延保、联系师傅和支付费用暂不形成首版业务流程。

铭牌档案不代替发票等保修凭证，系统按录入信息推算的状态也不保证厂家一定接受保修。

### 2.3 三个层次的期望

| 层次 | 用户期望 | 第一版如何回应 | 如何判断 |
|---|---|---|---|
| 功能 | 录得下、查得到、提醒能处理、故障建议与设备相关 | 九模块中的建档、查询、保修、保养、提醒及 AI 问答 | 用真实任务检查正确性与完成过程 |
| 情感 | 少担心遗忘、信息丢失和错误操作 | 主动提醒、人工核对、访问保护和备份恢复 | 访谈是否更有把握，是否仍需另记一份 |
| 共同使用 | 资料不只掌握在某一个人手里 | 同一空间扫码查看，管理权限保持独立 | 查看者能否不依赖负责人完成查询 |

不将“有成员排行、能展示贡献”作为共同使用的前提。第一版验证的是共享资料是否方便，而非社交传播或成员考核。

### 2.4 机会判断：先记录假设，再通过试用校准

现阶段没有统一量表的真实访谈数据，因此不沿用原稿的数字机会分，也不据此宣称某项需求已被证明更重要。

| 机会假设 | 判断依据 | 待验证问题 |
|---|---|---|
| 降低建档成本有助于开始使用 | 其他功能需要先有设备资料 | 拍照加核对，是否确实比手填更省事 |
| 扫码共享有助于独立查询 | 同一空间多人需要同一份资料 | 使用者是否能找到入口和对应设备 |
| 提醒有助于把计划变成处理动作 | 用户未必经常主动打开 | 提醒是否送达、是否有用、是否造成打扰 |
| 设备相关问答有助于初步排查 | 型号、品类与保修状态能提供背景 | 建议是否相关、安全，是否减少重复描述 |
| 数据可靠是持续保存资料的前提 | 档案需要跨时间使用 | 恢复是否可行，管理者是否信任保存方式 |

访谈可询问最近一次真实建档、查询或保养经历，记录原来怎么做、花多少时间、遇到什么问题。若后续评分，应使用一致量表并记录样本与时间；不以团队假设分数代替用户结果。

### 2.5 切换四力

| 力量 | 当前分析假设 | 第一版的对应设计 |
|---|---|---|
| 现有方式的推力 | 分散资料、反复询问和记忆周期可能带来麻烦 | 集中档案、保修计算和计划管理 |
| 新方案的吸引力 | 拍照录入、扫码查看和主动提醒可能减少操作 | 保留这三条入口，避免个人注册 |
| 使用焦虑 | 担心识别不准、资料公开、密码丢失或 AI 误导 | 可修改、查看与管理分离、密码恢复、安全提示 |
| 既有习惯 | 相册、纸笔和问人可能已经足够方便 | 比较真实任务成本，而非要求用户每天打开 |

四力用于提出试用问题，当前没有测量它们的强弱，不能推导“家人没用起来一定是某个原因”。

## 3. Pre-mortem：第一版可能怎样失败

### 3.1 假设的失败情境

设想第一版交付并试用一段时间后，出现以下情境：设备只在演示时录入，扫码后难以找到信息；提醒没有送达或反复发送；AI 给出与设备无关的回答；管理者仍回到相册、纸笔和询问他人的方式。

这是为了提前寻找薄弱环节而构造的情境，不是已经发生的结果，也不预设未来某一天必然失败。

### 3.2 风险、应对与检查方式

以下为团队的定性风险清单，不表示已测得发生概率。措施限于已确认的第一版范围，不附加未经确认的上线日期。

| 编号 | 风险 | 首版内的应对 | 检查方式 |
|---|---|---|---|
| R1 | 功能继续膨胀，核心流程迟迟不能交付 | 按范围基准限制各模块深度，新增需求先确认 | 任务与九模块及延期清单逐项对应 |
| R2 | 铭牌识别错误或等待过长，核对成本高 | 允许修正，失败可手填；记录识别耗时和错误 | 用真实铭牌检查字段与完整建档耗时 |
| R3 | 家人或师生扫码后仍找不到对应设备 | 展示当前空间、清楚命名设备、明确查看入口 | 观察不代操作的扫码查询 |
| R4 | 服务或通知链接无法从真实手机打开 | 核验可达访问入口、HTTPS和部署恢复说明 | 在目标手机及实际使用网络验证 |
| R5 | 查看二维码泄露管理权限或敏感资料 | 服务端区分查看与管理，按空间隔离数据 | 未授权读写、跨空间访问与照片链接检查 |
| R6 | 管理密码遗失，空间无人能维护 | 在实施前确定密码恢复与授权失效方式 | 演练恢复和更换密码后旧授权失效 |
| R7 | 保养模板不适合实际设备，日期计算失真 | 默认值可调整，展示上次与下次日期 | 修改周期、完成续期和月末日期检查 |
| R8 | 提醒未送达、重复发送或事项处理后仍催办 | 一个渠道先接通，定时检查、去重、更新处理状态 | 实际接收三类通知，重复扫描与处理后检查 |
| R9 | AI 混用其他设备信息，或给出危险建议 | 限定当前空间设备上下文，切换设备不混用；给出安全提示 | 真实多轮问答、切换设备与危险故障样例验证 |
| R10 | 换机或故障导致档案、照片无法恢复 | 基础备份覆盖业务数据与照片，限制恢复权限 | 在隔离环境恢复并核对归属和内容 |
| R11 | 团队把原型或历史测试当作当前完成证据 | 区分规划、代码、自测和用户实机验收 | 每项结论标注来源、时间与验证条件 |
| R12 | 没有真实管理需求，却用活跃次数判断价值 | 选择实际设备及真实任务试用，观察查询和处理结果 | 访谈是否愿意继续使用、是否仍需重复记录 |

备份恢复、空间权限和 AI 安全边界影响数据与使用可靠性，应随对应模块验证。测试发现问题时修复并复核，不为展示进度降低验收要求。

### 3.3 当前证据怎样使用

- 代码能说明现有功能入口和计算逻辑，不能证明真实手机、数据库或外部服务当前正常。
- 历史开发日志可帮助挑选回归场景，例如品类修正、周期调整和访问入口；不能据此认定问题现在仍然存在。
- 旧文档中的“库里只有 2 台”“家人没有自助使用”等不沿用为当前事实，真实数量和使用情况以本轮实际验收记录为准。
- 原稿的风险命中率、用户流失比例和指定日期排期没有足够当前证据，不继续作为汇报结论或开发承诺。

## 4. 将分析落实到验证

### 4.1 第一版交付验收

以下对应现有范围基准，没有新增评分门槛，结果待执行并记录。

| 验证事项 | 目标与证据 |
|---|---|
| 真实建档 | 家庭至少录入 10 台真实电器，检查字段、照片及所属空间 |
| 建档效率 | 对典型清晰铭牌实测完整建档，沿用 ≤30 秒目标，记录网络、模型条件和失败样例 |
| 独立查询 | 家人自行扫码找到指定设备并查到是否过保，不由开发者代操作 |
| 保养处理 | 管理者完成任务，核对完成日期、下一期及提醒状态 |
| 空间和权限 | 家庭、教室两个空间验证查看／管理边界和数据隔离 |
| 主动提醒 | 实际收到保修临期、保养到期和逾期通知，验证去重和旧提醒停止 |
| AI 助手 | 真实模型结合所选设备多轮回答；检查上下文切换、不确定性和安全建议 |
| 基础保障 | 手机核心操作、重启保留，以及隔离环境的业务数据与照片恢复 |

推送渠道、具体触发时间、密码恢复、二维码更换及 AI 会话方式等按范围基准的待定清单，在实施对应模块前确定。本文不擅自固定“每天几点发送”或新增第二个渠道。

### 4.2 持续价值观察

交付能用后，再记录下列问题：

- 管理者在真实需要时是否愿意补录、修正设备资料。
- 查看者能否独立获得答案，是否仍需要反复询问负责人。
- 提醒送达后是否能找到并处理事项，是否有误报或重复打扰。
- AI 回答是否帮助用户完成下一步判断，是否出现无关、错误或危险内容。
- 用户是否愿意继续保存资料，是否仍要在别处重复记录。

这些是补充试用观察，不自动增加第一版交付条件。家电管理是低频任务，不能仅凭一段时间没有新增设备或没有每天打开就认定失败；应结合期间是否有查询、保养、临期或故障需要。

### 4.3 跟进方式

先按路线图补齐空间权限和现有主线，再完成主动提醒与 AI 助手，各模块完成后留下验证记录。整体验收时汇总失败样例和用户反馈，区分实现缺陷与需求假设不成立，再决定后续调整。

本分析保留的核心判断是：先让用户在具体场景中把任务办成，再判断是否值得继续使用；既不以页面数量替代产品价值，也不以未发生的使用场景制造失败结论。

## 5. 汇报速查

| 问题 | 当前回答 |
|---|---|
| 谁在使用 | 以家庭为主要试用场景，同时验证教室等空间；区分管理任务与查看任务，不设个人成员体系 |
| 要完成什么 | 方便建档、扫码查询、查清保修、按期保养和故障初步排查 |
| 为什么采用空间共享 | 同一空间的人共用资料，查看无需个人注册，修改仍受管理权限控制 |
| 为什么保留提醒和 AI | 提醒连接到期事项与处理动作；AI 结合档案支持初步排查，两者已纳入第一版 |
| 第一版怎样做减法 | 限制各模块内部深度，暂缓成员管理、完整维修记录、统计和交易流程 |
| 最大的待验证问题 | 录入是否省事、扫码是否方便、提醒是否有用、AI 是否相关安全、数据是否可靠 |
| 怎样确认成果 | 按范围基准执行真实任务验收，另行观察实际使用，不把规划写成已完成 |
